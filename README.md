# AoE2 unranked group ladder + Discord bot

A private Elo ladder for a group of nine Age of Empires II players, built from their
**unranked lobby games** scraped from [aoe2insights.com](https://www.aoe2insights.com/),
and a Discord bot that uses those ratings to pick balanced teams for the next game.

## Commands

| Command | What it does |
|---|---|
| `/balance [map]` | Pick players from a menu, get the two most evenly matched teams |
| `/players [map]` | Elo table, overall or for one map |
| `/playerstats <player> <map>` | Map Elo + rank, W/L, recent form, most-played civs |

With a `map` argument the bot rates players by their per-map Elo, falling back to overall
Elo (marked `*`) for anyone with fewer than 5 games on that map.

## Layout

```
code/     the Discord bot
  bot.py           slash commands and embeds
  ladder_data.py   loading + rating logic (no discord.py import, so it's testable)
  team_balancer.py splits a set of rated players into two even teams
data/     the scrape + rating pipeline
  ladder_common.py            shared config, paths, parsing, qualifying filter, Elo
  incremental_update.js       browser-side scraper, injected into the debug Chrome
  fetch_incremental_update.py drives that Chrome over CDP, then rebuilds everything
  run_full_refresh.py         all the non-browser rebuild steps
  build_*.py                  the ladders: overall, per-map, open/closed
deploy/   systemd units for the Ubuntu server
scripts/  publish_update.ps1 - the nightly job on the Windows PC
tests/    python3 -m unittest discover -s tests
```

## How it runs

Two machines, with git as the transport:

| Step | Machine | Why |
|---|---|---|
| Fetch from aoe2insights + rebuild the ladders | Windows PC | needs the manually-prepared debug Chrome (Cloudflare) |
| Publish (`scripts/publish_update.ps1`) | Windows PC | commits the new JSON, pushes to GitHub |
| Pull (`deploy/pull.sh` via timer) | Ubuntu server | fast-forwards the repo every 15 min |
| Serve `/balance` etc. | Ubuntu server | `aoe2bot.service` |

No bot restart is needed after a data update — `bot.py` re-reads the JSON whenever it
changes on disk. Setup for both machines is in [`deploy/README.md`](deploy/README.md).

## Running the bot

```bash
pip install -r code/requirements.txt
export DISCORD_BOT_TOKEN=...        # never commit this
python3 code/bot.py
```

Paths default to the repo layout. Override with `DATA_DIR`, or point at individual files
with `LADDER_PATH` / `MAP_ELO_PATH`.

## Running the pipeline

```bash
pip install -r data/requirements.txt
powershell -File data/launch_chrome_debug.ps1   # then solve the Cloudflare check, leave open
python3 data/fetch_incremental_update.py        # scrape + rebuild + refresh known_ids
```

`run_full_refresh.py` does everything except the scrape, so it's the one to run after
editing something by hand. Every script defaults to reading and writing this repo's
`data/` directory; set `DATA_DIR` to keep the working data elsewhere.

## How the rating works

Elo, K=32, everyone starting at 1000, over unranked matches since 2024-01-01 where **two
or more tracked players are on opposing teams**. Untracked lobby players are ignored for
rating purposes. Each player is rated against the average Elo of the tracked opponents
facing them.

Excluded from the calculation: matches under 15 minutes (too short to be conclusive,
whether or not an AI was in the game), and matches whose winner can't be established.
The scraped files in `data/unranked_raw/` are never modified by any of this.

Where per-match performance data exists, the score fed into the Elo update is no longer a
flat win/loss, so a dominant win gains more than a narrow one. Win/loss still fixes the
direction. Only roughly the last 8–9 months of games have that data available.

`map_elo.json` and `openclosed_elo.json` are separate, win/loss-only ladders that each
restart every player from 1000. **Their numbers are only comparable within one map** —
the bot rescales them onto the overall ladder before balancing with them (see
`ladder_data.map_adjusted_elos`).

## Known gap

The published `data/unranked_ladder.json` was generated by a newer "v2" scoring script
(`config.performance_ratio_v2`, a `0.75·result + 0.25·performance` blend over military
production, APM and tech signals) that **is not in this repo** — `build_unranked_ladder.py`
here is the earlier revision. So the committed data can't be reproduced from the committed
code, and two changes need porting into whatever local copy produces the published file:

- the undecidable-result handling in `ladder_common.resolve_won_flags`
- the extra performance signals its `__extractPerf` collects

Until then, the published ladder still carries the deflation that fix removes.
